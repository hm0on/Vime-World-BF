## 📦 Использование

### Быстрая установка

Откройте терминал в папке проекта. Нужен **Python 3.11 или новее**.

**Linux / macOS:**

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

**Windows PowerShell:**

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

### Подготовка файлов

Создайте рядом с `main.py` три файла или заполните существующие:

| Файл | Содержимое |
| --- | --- |
| `users.txt` | Значения первого JSON-параметра, по одному на строку. |
| `passwords.txt` | Значения второго JSON-параметра, по одному на строку. |
| `proxys.txt` | Прокси, по одному на строку. |

Каждая уникальная строка `users.txt` проверяется со всеми уникальными строками `passwords.txt`.
Совпадение сохраняется, после чего перебор продолжается. Одинаковые пары повторно
не отправляются, в том числе после перезапуска с той же историей.

Пустые строки пропускаются, дубликаты удаляются, UTF-8 BOM поддерживается.
Пробелы внутри значений и по краям сохраняются. Пути считаются от папки программы.

### Настройка API

Все настройки находятся в [`config.py`](config.py). Укажите адрес API, имена
параметров:

```python
API_URL = "https://your-api.example/check"
PARAM1_NAME = "param1"
PARAM2_NAME = "param2"
```

Это пример — замените значения на свои. В `HEADERS` можно добавить заголовки API,
а в `EXTRA_JSON` — постоянные поля тела запроса.

Выберите способ определения результата в `config.py`:

```python
RESULT_MODE = "status"  # "status" — HTTP-статус, "json" — JSON-ответ
```

**Режим `status`** (выбран по умолчанию) не читает тело ответа:

| HTTP-статус | Результат |
| --- | --- |
| `200` | `match` — совпадение, пара попадает в экспорт. |
| `400` | `no_match` — несовпадение. |
| `429` | `rate_limited` — сервер ограничил частоту запросов; выводится предупреждение. |
| Остальные | `http_error` — ошибка HTTP, без записи в совпадения. |

Ошибка соединения или таймаут сохраняется как `network_error`.
**Режим `json`** использует настройки:

```python
RESULT_MODE = "json"
MATCH_JSON = {"match": True}
NO_MATCH_JSON = {"match": False}
RESPONSE_MATCH_MODE = "subset"  # "subset" или "exact"
```

При `subset` проверяются указанные поля, включая вложенные; при `exact` — весь JSON.
Правило `MATCH_JSON` означает совпадение, `NO_MATCH_JSON` — несовпадение.
Если не подошло ни одно правило или подошли оба, результат — `unknown`.
Некорректный JSON или превышение `MAX_RESPONSE_BYTES` дают `response_error`.
JSON анализируется для HTTP 2xx и 4xx, кроме `429`: он всегда остаётся ошибкой
`rate_limited`. Перенаправления и HTTP 5xx считаются `http_error` независимо от JSON.

У режимов отдельная история. Переключение на другой режим не смешивает результаты;
возврат к предыдущему продолжает его историю. В режиме `status` JSON-настройки
не используются.

### Запуск

```sh
python main.py
```

Чтобы остановить программу, нажмите **Ctrl+C**. Завершённые проверки сохраняются,
совпадения экспортируются в `matches.jsonl`.

| `RETRY_ERRORS_ON_NEXT_RUN` | Повторить ошибочные и неопределённые пары при следующем запуске. |
| `RUN_NAMESPACE` | Измените значение, чтобы намеренно начать проверку заново. |
| `SHOW_PROGRESS` | Включить живой экран; при `False` остаётся итоговая панель. |
| `UI_REFRESH_PER_SECOND` | Частота обновления интерфейса. |
| `LOG_FILE` | Путь к файлу логов. |
| `CONSOLE_LOG_LEVEL`, `FILE_LOG_LEVEL` | Уровни логов консоли и файла. |
| `LOG_ROTATION`, `LOG_RETENTION` | Ротация и срок хранения логов. |

Свободный воркер сразу берёт следующую пару, не ожидая всю предыдущую группу.
Несколько пятёрок могут выполняться одновременно, но каждые пять назначенных
отправок используют следующий прокси по кругу. Ошибки тоже учитываются в пятёрке.
При новом запуске отсчёт прокси начинается сначала; с одним прокси адрес не меняется.
Перенаправления и автоматические повторы внутри запуска отключены.

Клиенты и соединения переиспользуются. Активные клиенты не закрываются при
вытеснении, поэтому кэш временно может превышать `MAX_CACHED_CLIENTS`.
Число воркеров ограничено `CONCURRENCY`; всё произведение двух файлов в память
не загружается. Реальная скорость зависит от API, прокси и сети.

При `RETRY_ERRORS_ON_NEXT_RUN = False` обработанные пары не повторяются даже
после технической ошибки. При `True` ошибки, включая `rate_limited`, можно повторить в следующем
запуске; однозначные совпадения и несовпадения всё равно пропускаются.

Адрес API, имена параметров, дополнительные поля, заголовки, режим определения результата и
`RUN_NAMESPACE` определяют профиль истории. Их изменение создаёт отдельный профиль.
Экспорт содержит совпадения только текущего профиля.
Правила JSON также определяют профиль в режиме `json`. История режима `status`
сохраняет совместимость с предыдущей версией.

Запускайте одну копию программы с одной базой. Если прервать запрос до сохранения
ответа, его исход останется неизвестен и при перезапуске он может повториться.
Гарантия «ровно один раз» требует поддержки идемпотентности на стороне API.

## 💡 Примеры работы

### Пример №1: перебор комбинаций

Содержимое `1.txt`:

```text
alpha
beta
```

Содержимое `2.txt`:

```text
red
blue
```

**Запускаем программу** — будут отправлены четыре уникальные пары:

```json
{"param1": "alpha", "param2": "red"}
{"param1": "alpha", "param2": "blue"}
{"param1": "beta", "param2": "red"}
{"param1": "beta", "param2": "blue"}
```

Если для `alpha + red` сервер вернёт HTTP `200`, в `matches.jsonl` появится:

```json
{"param1": "alpha", "param2": "red"}
```

Остальные комбинации продолжат проверяться. Из-за асинхронности ответы и строки
экспорта могут приходить в другом порядке.

---

### Пример №2: разные типы прокси

Содержимое `proxys.txt`:

```text
http://user:password@127.0.0.1:8000
socks4://127.0.0.1:1080
socks4://user@127.0.0.1:1081
socks5://user:password@127.0.0.1:1082
socks5h://127.0.0.1:1083
```

**Запускаем программу** — первые пять отправок назначаются первому прокси,
следующие пять — второму, затем третьему и так далее по кругу.

Типы можно чередовать в любом порядке. Без префикса строка `host:port` считается
HTTP-прокси; для SOCKS укажите `socks4://`, `socks5://` или `socks5h://`.
Также поддерживается `https://` для соединения с самим прокси по TLS.
SOCKS4 использует USERID без пароля. Спецсимволы в логине и пароле кодируются как в URL.

---

### Пример №3: статистика и результаты

Пример отображения CLI (цифры условные):

```text
╭────────────────────────── POST · PAIR CHECKER ──────────────────────────╮
│ Проверка ━━━━━━━━━━━━━━━━━━━╸━━━━━━━━ 65% 650/1000 42.3 req/s ETA 00:00:08│
│                                                                        │
│ Совпадения: 12        Несовпадения: 620       Ошибки / неизвестные: 8     │
│ В работе: 20 / 50     Из истории: 10         Средний ответ: 235 ms       │
│ Прокси: 8            Смена через 5 отправок  Завершено за запуск: 640    │
╰──────────── Ctrl+C — остановить и сохранить результаты ─────────────────╯
```

Rich показывает прогресс, среднюю скорость завершённых запросов за текущий запуск,
прошедшее время, ETA, задержку ответа и число активных запросов. История учитывается
в прогрессе, но не увеличивает req/s. ETA оценочный и может быть завышен,
пока программа ещё не прочитала всю историю.

Результаты после работы:

| Файл | Что сохраняется |
| --- | --- |
| `matches.jsonl` | Совпавшие пары текущего профиля; экспорт при завершении или Ctrl+C. |
| `results.sqlite3` | Все завершённые проверки, HTTP-коды, JSON-ответы в режиме JSON и типы ошибок; запись сразу. |
| `logs/checker.log` | События Loguru: время, уровень, идентификатор пары, статус и длительность. |

Статусы новых проверок: `match`, `no_match`, `network_error`, `http_error`, `rate_limited`, `response_error`, `unknown`. Входные значения, тела ответов, токены и пароли прокси не выводятся в логи.
В режиме `json` разобранные ответы сохраняются в SQLite, в режиме `status`
тела ответов не читаются. Файловые логи пишутся через отдельную очередь,
с ротацией по `10 MB` и хранением за `7 days` при стандартных настройках.
Чтобы не записывать каждую попытку, установите `FILE_LOG_LEVEL = "INFO"`.
