# Проверка пар через POST

Python 3.11+. Все настройки находятся в `config.py`; файлы читаются из папки
программы независимо от текущей директории терминала.

## Запуск

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

В Windows вместо `source` используйте `.venv\Scripts\activate`.

Перед запуском:

1. Укажите `API_URL`, `PARAM1_NAME`, `PARAM2_NAME` в `config.py`.
2. Заполните `1.txt`, `2.txt`: одна строка — одно значение.
3. Заполните `proxys.txt`: один прокси на строку. Поддерживаются `host:port`,
   `http://user:password@host:port`, `https://host:port`,
   `socks4://host:port`, `socks4://user@host:port`,
   `socks5://user:password@host:port` и `socks5h://host:port`.
   HTTP, SOCKS4 и SOCKS5 можно чередовать в любом порядке в одном файле.
   Строки без префикса считаются HTTP-прокси; для SOCKS префикс обязателен.
   SOCKS4 использует только имя пользователя (USERID), без пароля.
   Спецсимволы в логине/пароле нужно кодировать как в URL.
4. Укажите `MATCH_JSON` и `NO_MATCH_JSON` — признаки совпадения и несовпадения.

Например:

```python
MATCH_JSON = {"result": {"valid": True}}
NO_MATCH_JSON = {"result": {"valid": False}}
```

При `RESPONSE_MATCH_MODE = "subset"` проверяются только указанные ключи,
включая вложенные. При `"exact"` весь JSON должен совпасть целиком.
Списки сравниваются по длине и порядку; объекты внутри них следуют выбранному режиму.
Если подошли оба правила или не подошло ни одно, результат — `unknown`.
Только HTTP 2xx с JSON, соответствующим одному правилу совпадения, считается мэтчем.

## Перебор и скорость

Для каждой уникальной строки `1.txt` проверяются все уникальные строки `2.txt`.
Совпадение не останавливает перебор. Пустые строки пропускаются, BOM UTF-8
поддерживается, пробелы в значениях сохраняются. Дубликаты строк удаляются.

Запросы асинхронные, без искусственной задержки, по умолчанию до 20 одновременно.
Пять отправок идут через первый прокси, следующие пять — через второй и так далее
по кругу. Следующие отправки не ждут самый медленный ответ предыдущей пятёрки:
несколько групп могут находиться в работе одновременно. Ошибки тоже учитываются
в пятёрке; перенаправления и автоматические повторы отключены.
Нумерация групп прокси начинается сначала при каждом запуске.
При одном прокси адрес остаётся тем же после каждой пятёрки.

`CONCURRENCY` регулирует общий лимит параллельности независимо от `REQUESTS_PER_PROXY`.
Пары выбираются в порядке первого файла, затем второго, но ответы
могут приходить в другом порядке. Отдельные потоки для ожидания сети не нужны.
Скорость зависит от API, прокси и сети; каждая завершённая проверка сразу сохраняется.
Свободный воркер сразу получает следующую пару. Число задач ограничено
`CONCURRENCY`, всё произведение файлов в память не загружается.

Кэш клиентов повторно использует TCP/TLS-соединения после нового круга прокси.
`MAX_CACHED_CLIENTS` ограничивает число кэшированных клиентов; используемые клиенты
не закрываются, поэтому временно кэш может превышать этот лимит, пока они заняты.
Сертификаты TLS загружаются один раз, история проверяется одним запросом на строку
первого файла вместо отдельного запроса на каждую пару.

## CLI и логирование

Rich показывает прогресс, среднюю скорость завершённых запросов в секунду за текущий
запуск, прошедшее время, ETA, среднее время запроса, число активных запросов,
совпадения, несовпадения, ошибки и пропущенные пары из истории.
Пары из истории учитываются в прогрессе, но не увеличивают показатель req/s.
ETA оценочный: при ещё не прочитанной истории он может быть завышен.
`SHOW_PROGRESS = False` отключает живой экран, оставляя итоговую панель.
`UI_REFRESH_PER_SECOND` задаёт частоту обновления (по умолчанию 4 Гц).

Loguru пишет события запуска/остановки в консоль, а подробные статусы попыток — в
`logs/checker.log`. Запись файла выполняется через отдельную очередь, чтобы не
задерживать сетевые задачи. В логе есть время, уровень, идентификатор пары,
статус, HTTP-код и длительность; входные значения, тела ответов, токены и пароли
прокси не выводятся. Полные ответы остаются в SQLite.

Настройки: `LOG_FILE`, `CONSOLE_LOG_LEVEL`, `FILE_LOG_LEVEL`, `LOG_ROTATION`
(по умолчанию `"10 MB"`), `LOG_RETENTION` (по умолчанию `"7 days"`).
При `FILE_LOG_LEVEL = "INFO"` отдельные попытки не пишутся, что уменьшает объём лога.
Перед первым запуском после обновления установите зависимости:

```sh
python -m pip install -r requirements.txt
```

## Результаты и повторный запуск

- `results.sqlite3`: все пары, их статусы, HTTP-коды, JSON-ответы или типы ошибок.
- `matches.jsonl`: только совпавшие пары текущего профиля, по одному JSON на строку.
  Экспорт обновляется при завершении или Ctrl+C, данные SQLite пишутся сразу.
- `match` / `no_match`: однозначный ответ; `network_error`, `http_error`,
  `response_error`, `unknown`: техническая ошибка или неопределённый результат.

История не позволяет повторно отправлять обработанные пары, в том числе после
перезапуска. При `RETRY_ERRORS_ON_NEXT_RUN = False` даже ошибочные пары не повторяются;
`RETRY_ERRORS_ON_NEXT_RUN = True` разрешает повторить их при следующем запуске.
Совпадения и несовпадения при этом не повторяются.

Чтобы намеренно начать заново, измените `RUN_NAMESPACE`. Изменение адреса,
имён параметров, дополнительных полей, заголовков или правил ответа также создаёт
отдельную историю. Экспорт содержит совпадения только текущего профиля.

Запускайте одну копию программы с одной базой. Если процесс прервать во время
отправки или аварийно завершить до записи результата, исход такой попытки неизвестен:
при следующем запуске она может повториться. Строгое «ровно один раз» для POST
возможно только с поддержкой идемпотентности со стороны API.

Для проверки реализации без внешних запросов:

```sh
python -m unittest discover -s tests -v
```
